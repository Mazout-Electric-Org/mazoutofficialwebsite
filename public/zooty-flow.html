System Design Document — v1.0

Zooty.
Last-Mile Campus Delivery

Autonomous locker-on-wheels bridging third-party delivery platforms (Blinkit / Zomato) to hostel students via WhatsApp-native order management and teleoperated delivery.

01 — Problem Statement

The Last 500 Metres Problem

Delivery platforms (Blinkit, Zomato) stop at the university gate. The student is sitting in a hostel block that's a 5–15 minute walk inside campus. The delivery person cannot enter. The student has to drop everything and come to the gate or miss the delivery entirely.

Zooty eliminates this by acting as an autonomous, teleoperated locker vehicle that picks up the order at the gate and drives it to the exact drop location, controlled by a campus admin. No app install required — the entire student experience runs on WhatsApp.

02 — End-to-End Operational Flow

10-Step Delivery Lifecycle

Every order follows a deterministic 10-step lifecycle from student registration to parcel collection. Each step has a responsible actor (Student / Admin / System) and a communication channel.

STEP 01

Student Registers Order on WhatsApp Bot

Student initiates Zooty bot. Bot collects: Name, Order No., Platform, Item Amount, Pickup Location (gate), Drop Location (hostel block + room), Alt Phone.

WhatsApp Bot
STEP 02

Confirmation & Backend Sync

Bot shows a structured summary. Student confirms. Payload is sent to AWS backend via REST API and immediately reflects on Admin Dashboard.

Admin Dashboard
STEP 03

Admin Assigns Zooty Unit

Admin reviews open orders dashboard and assigns an available Zooty (e.g., Zooty101) to the order. Zooty is teleoperated to the pickup location (gate).

Admin + Telemetry
STEP 04

Student Gets Assignment Notification

WhatsApp bot pushes: "Zooty101 assigned to you. Share this ID with the delivery person." Zooty is on the way towards gate.

WhatsApp Bot
STEP 05

Delivery Person Loads the Order

Delivery person arrives at gate with parcel. Admin monitors gate camera feed. Once confirmed, admin remotely opens Zooty's container door. Parcel is placed inside. Door auto-closes.

Zooty Unit
STEP 06

Order Confirmed Loaded + ETA Notification

System sends: "Your order is loaded. Zooty101 is on the way — ETA 3 min." Admin drives Zooty via telemetry to the drop location.

WhatsApp Bot
STEP 07

Zooty Arrives at Drop Location

Admin parks Zooty at hostel block. System pushes notification with: arrival alert + UPI QR code image for delivery fee payment.

Payment
STEP 08

Student Pays — Container Unlocks

Payment verified via UPI webhook. Only on successful payment confirmation does the "Open Container" option become active on Admin Dashboard. No payment = box stays locked.

Payment Gate
STEP 09

Admin Opens Box — Student Collects

Admin opens container remotely. Student collects parcel. Order is marked as Delivered in the system.

Zooty Unit
STEP 10

Feedback & Session Close

Bot sends: "Thanks! How was your Zooty experience?" — single-question feedback. Session auto-closes after 60 seconds if no response. Zooty returns to hub.

WhatsApp Bot

05 — Proposed Tech Stack

Implementation Stack

Every technology choice has a concrete rationale. Nothing exotic — all battle-tested with strong community support and free/cheap tiers for a campus pilot.

Bot Layer
Meta WhatsApp Cloud API
Free tier. No phone number hosting cost. Webhooks for inbound messages.
Bot Logic
Node.js (Express)
Session state machine per student. Redis for session persistence.
API Layer
AWS API Gateway + Lambda
Serverless. Pay per request. No idle cost during low traffic.
Database
DynamoDB
Orders, sessions, users. Fast key-value lookups. Auto-scaling.
IoT Comm
AWS IoT Core (MQTT)
Bidirectional Zooty ↔ backend. Telemetry commands + GPS data.
Admin UI
React + Mapbox GL
Live GPS tracking, order management, remote container control.
Payment
Razorpay / Cashfree
Dynamic UPI QR generation. Webhook for payment confirmation.
Zooty Hardware
MP2 Module
Pi handles comms/camera. Arduino handles motor/lock control.
Camera
WebSocket (mediasoup)
Low-latency live feed to admin dashboard for gate monitoring.
Notifications
AWS SQS + SNS
Async event queue decouples notification sending from order logic.
06 — Risks & Mitigations

Known Risks

Every system has failure modes.

Risk Impact Severity Mitigation
Payment webhook delay — door stays locked after student pays Poor UX, student frustration HIGH Implement idempotent retry logic on webhook. Admin override button always available.
Delivery person doesn't know which Zooty is theirs Wrong parcel in wrong Zooty HIGH Physical Zooty ID label (QR + number). Admin verifies via camera before opening door.
Campus Wi-Fi dead zones — Zooty loses MQTT connection mid-route Zooty stuck, admin loses control HIGH SIM card (4G) fallback on MP2 Module. Fail-safe: Zooty stops in place, admin notified.
WhatsApp session expires before delivery completes Student misses notifications MEDIUM Use WhatsApp Business "utility" message templates.
Battery dies during delivery Order stuck mid-route MEDIUM Low battery alert triggers admin; admin drives Zooty to nearest hub first. Battery threshold: 20%.
Student doesn't pick up parcel after box opens Parcel exposed, vulnerable LOW 2-minute auto-close on container. Admin can re-open. Notify student again after 5 min.
07 — MVP Scope for Pilot

What to Build First

For a campus pilot, focus on validating the core loop: student registers → order gets to room → student pays and collects.

MUST HAVE — MVP

Core Delivery Loop

WhatsApp bot data collection, AWS backend, admin dashboard with manual Zooty assignment, basic MQTT telemetry, UPI payment gate before box opens.

Phase 1
SHOULD HAVE — V2

Reliability & Automation

GPS live tracking on dashboard, camera feed integration, auto-ETA calculations, payment webhook retry logic, low battery alerts.

Phase 2
NICE TO HAVE — V3

Scale & Intelligence

Multi-Zooty routing, automated Zooty assignment based on proximity, student order history, analytics dashboard, battery swap scheduling.
